# Astro Sushil Staging Operations, Data Safety & Observability Manual

This specification details operational procedures, database maintenance, data safety, R2 storage monitoring, logging, rollback steps, and smoke-testing protocols for the **Astro Sushil Staging Environment**.

---

## 1. Staging Identity & Isolation

To prevent accidental data loss or cross-contamination with production infrastructure, all staging components follow a strict naming convention:

| Component | Staging Name / Identifier | Isolation Protocol |
| :--- | :--- | :--- |
| **Node Environment** | `NODE_ENV=production` | Built for production optimization, but isolated from live traffic. |
| **API Domain** | `https://astrosushil-api-staging.onrender.com` | Deployed on Render Staging Web Service. |
| **Admin Domain** | `https://astrosushil-admin-staging.vercel.app` | Deployed on Vercel Staging project. |
| **PostgreSQL Database** | `astro-sushil-staging-db` | Dedicated Supabase project database instance. |
| **Redis Cache & Queue** | `astro-sushil-staging-redis` | Dedicated Upstash Redis staging cluster. |
| **Object Storage Bucket** | `astro-sushil-reports-staging` | Private Cloudflare R2 staging bucket. |
| **Payment Gateway** | Razorpay TEST Mode | Uses `rzp_test_...` key pairs; live transactions prohibited. |
| **Gemini AI** | Staging API Key | Dedicated API key with strict usage quotas. |

## 2. Staging Database Safety & Maintenance

### A. Connection
Connection to Supabase Staging PostgreSQL is configured via the environment variable `DATABASE_URL`. The schema is managed exclusively using Prisma.

```bash
# Verify schema status against Staging PostgreSQL
npx prisma status
```

### B. Migration Procedure
All schema updates must be deployed via declarative Prisma migrations:
```bash
npx prisma migrate deploy
```

### C. Safe Staging Reset & Cleanup Procedure
To clear stale test records generated by QA automated testing, run the staging cleanup script.

> [!CAUTION]
> The staging cleanup procedure is guarded by `NODE_ENV` and explicit confirmation flags to prevent execution against production databases.

```bash
# Run staging database and R2 storage cleanup (Staging Only)
npm run db:clean:staging
```

## 4. Cloudflare R2 Storage Monitoring & Policy

- **Bucket Name**: `astro-sushil-reports-staging`
- **Access Control**: Private — public read access is disabled (`X-Amz-ACL: private`).
- **Object Key Structure**: `reports/{userId}/{reportId}.pdf`
- **Signed URL Expiration**: Presigned download URLs expire after **900 seconds (15 minutes)**.

---

## 5. Storage & Database Consistency Verification

To detect orphaned records or missing binary objects:

1. **Database Report Exists, R2 Object Missing**:
   The report record status transitions to `FAILED` with `errorCode: OBJECT_STORAGE_MISSING`.
2. **R2 Object Exists, Database Report Missing**:
   Detected via `StorageService.cleanupOrphanedObjects(validKeysSet)`.

## 6. Structured Logging & Observability

Backend services enforce structured JSON logging via `@astro/api/src/utils/logger.ts`.

### Job Stage Log Markers
- `REPORT_GENERATION_STARTED` — Triggered when BullMQ receives report job.
- `REPORT_PDF_GENERATED` — XeLaTeX compilation completed.
- `REPORT_PDF_VALIDATED` — Automated QA validator checks page count and placeholders.
- `REPORT_UPLOADED` — Uploaded binary buffer to Cloudflare R2.
- `REPORT_COMPLETED` — DB status updated to `COMPLETED`.
- `REPORT_GENERATION_FAILED` — Exception trapped; job marked as `FAILED`.

### Sensitive Field Scrubbing
The logger automatically redacts the following keys from log payloads:
`password`, `passwordHash`, `token`, `accessToken`, `refreshToken`, `authorization`, `secret`, `apiKey`, `r2SecretAccessKey`, `razorpaySecret`, `geminiKey`.

## 7. Health Checks & Worker Heartbeat

### Liveness Probe (`GET /health`)
Returns HTTP 200 uptime status:
```json
{
  "status": "ok",
  "timestamp": "2026-09-02T04:30:00.000Z",
  "service": "astro-api",
  "environment": "production"
}
```

### Readiness Probe (`GET /ready` & `GET /health/ready`)
Checks database and cache connectivity:
```json
{
  "status": "ok",
  "timestamp": "2026-09-02T04:30:00.000Z",
  "service": "astro-api",
  "environment": "production",
  "database": "connected",
  "redis": "connected"
}
```

## 8. Rollback Protocol

If a staging release fails QA:

1. **API / Worker Rollback**: Redeploy previous Git commit tag on Render dashboard.
2. **Admin Rollback**: Promote previous deployment build in Vercel dashboard.
3. **Database Migration Safety**: Migrations must be strictly backward-compatible (add columns as nullable; do not drop columns in active use).

## 9. Staging Smoke-Test Execution Guide

Execute the 20-step smoke test before approving any build:

1. `GET /health` $\rightarrow$ Expect `status: "ok"`.
2. `POST /api/v1/auth/register` $\rightarrow$ Create test user.
3. `POST /api/v1/auth/login` $\rightarrow$ Receive JWT access & refresh tokens.
4. `POST /api/v1/auth/refresh` $\rightarrow$ Verify single-flight refresh token rotation.
5. `POST /api/v1/birth-profiles` $\rightarrow$ Save birth profile (Date, Time, Lat/Long).
6. `GET /api/v1/astrology/chart` $\rightarrow$ Calculate planetary positions and houses.
7. `POST /api/v1/jyoti/chat` $\rightarrow$ Send question to Jyoti AI assistant.
8. `POST /api/v1/reports/career` $\rightarrow$ Request Career Report job creation (`status: QUEUED`).
9. `GET /api/v1/reports/:id/status` $\rightarrow$ Poll worker progress (`CALCULATING` $\rightarrow$ `COMPILING` $\rightarrow$ `COMPLETED`).
10. `GET /api/v1/reports/:id/download-access` $\rightarrow$ Request presigned download URL.
11. Download PDF file $\rightarrow$ Confirm 68 pages, no forbidden placeholders.
12. Attempt cross-tenant download with User B token $\rightarrow$ Expect `403 Forbidden`.
13. Admin Login $\rightarrow$ Access Admin Portal at `https://astrosushil-admin-staging.vercel.app`.
14. Inspect Report Diagnostic in Admin $\rightarrow$ Verify duration, version, and file size.
